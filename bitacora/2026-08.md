# Bitácora — agosto 2026

## Flujo de ramas y despliegues

**Decisión:** `main` representa producción y no se usará para trabajo directo.
Cada tarea se desarrollará en una rama temporal (`feature/...`, `fix/...` o
`docs/...`), que se subirá al repositorio y se integrará mediante Pull Request
solo después de verificarla.

**Motivo:** Render tiene el despliegue automático activo y Vercel usa `main`
como rama de producción. Un `push` a `main` puede publicar cambios sin una
revisión previa, mientras que los commits locales no activan despliegues.

**Flujo acordado:**

1. Crear una rama por tarea desde `main`.
2. Hacer commits y pushes únicamente en esa rama.
3. Ejecutar las pruebas del backend y las verificaciones de lint/build del web.
4. Revisar el preview de Vercel cuando existan cambios frontend.
5. Abrir un Pull Request y hacer merge a `main` solo con autorización.
6. Verificar salud y endpoints principales después del despliegue.

**Reglas operativas:**

- `main` debe protegerse en GitHub para impedir pushes directos y exigir Pull
  Request con verificaciones exitosas.
- Render y Vercel pueden desplegar producción después del merge a `main`.
- La rama de trabajo no se considera producción; los previews no sustituyen la
  verificación posterior al despliegue.
- El workflow programado de sincronización Meta mantiene su ejecución sobre la
  rama principal y no debe usarse como mecanismo de publicación de código.

**Alcance inicial:** esta decisión aplica desde esta fecha a cambios de código,
documentación, configuración y scripts del proyecto.
